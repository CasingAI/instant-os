# 01 · 过墙通道 MVP 验证计划

> 建立时间：2026-08-25
> 修订：2026-08-26，见文末「修订记录」
> 前置：选型结论见 [00-overview.md](./00-overview.md) §4。
> 定位：**先于任何正式实现执行**。00 号文档的接入清单全部建立在本计划判定「通道可用」之上。

## 1. 为什么必须有这一步

§4 选型建立在三个未经实证的假设上，本 MVP 把它们逐个变成「已实测」：

1. **机制层**：宿主 TS 能在运行时往 io 表塞 read 处理器，客机执行 `IN` 能拿到值。
2. **权限层**：XP 里用户态程序发起的 `IN` 真能到达那个处理器（§8.3 的机制描述已被修订，唯一可信的是实测）。
3. **语义层**：值变化后轮询方能在合理延迟内感知。

## 2. 宿主侧：约 30 行测试模块

独立小模块（如 `guest-channel-test.ts`）：

- 注册 `ports[0xE000]` 的 `read8/read16/read32`，闭包存当前打包值 `(w<<16)|h`；
- 控制台钩子（如 `window.__setChannelValue(v)`）改闭包里的值；
- 用 `isDebugMode()` 门控，不碰协议、不加配置项（符合 00 号文档「开关未开时行为完全一致」原则）。

接线点：`v86-runtime.ts` 创建 emulator 之后（与 `installAbsoluteMouseRemap(next.bus, ...)` 同一位置附近）。三个位宽都挂——read8 是给第 1 级用的（见下）。

## 3. 客机侧：三级递进

每级成本极低，按序执行，任一级通过即回答对应问题。

### 第 1 级（零构建，先做）：XP 自带 `debug.exe`

XP 命令行自带 debug.exe，`i` 命令可从端口读字节：

```
C:\>debug
-i E000
78
```

不用写代码、不用编译器、不用改镜像。因为 debug 只有字节宽度，宿主要挂 read8（返回打包值最低字节）。

回答两个问题：

- NTVDM 会不会吞掉端口访问（16 位 VDM 任务对 IO 的处理在真实硬件上由内核代为仲裁，v86 下走不走得通没人知道）；
- 控制台改值后再 `-i` 一次能看到新字节 → 机制层 + 权限层一次性验证完毕。

### 第 2 级：FreeDOS 软盘 + ~20 行 NASM

绕开 NT 全家，验证通道在最裸环境下工作。循环轮询版：宿主改值，屏幕上数字自己跳——即验收第一条的雏形。

```nasm
mov dx, 0xE000
in  eax, dx          ; 386+ 的 32 位 IN
; 转 hex 后 int 10h teletype 打印，循环比对变化
```

协议里 `fda` 槽位现成，instant-app 加载软盘镜像路径已存在。软盘镜像按惯例不进 git（与 00 号文档 §7 约定一致）。

### 第 3 级：原生 32 位 XP 小工具

zig 或 llvm-mingw，单文件几十行（`_inpd()` 循环打印）。最终部署形态，给出权限层的最终答案。

## 4. 判定矩阵

| 结果 | 结论 |
|---|---|
| 第 1 级通 | 最理想；机制+权限双层全通，直接进正式实现 |
| 第 1 级不通、第 2 级通 | NTVDM 在中间拦截；不影响部署形态（原生工具不走 NTVDM），走第 3 级确认 |
| 第 2 级通、第 3 级不通 | v86 对保护模式 IN 存在意料外的检查（如 IOPL），需查 v86 源码定位 |
| 全不通 | 端口方案推翻；回退到 00 号文档 §8.1 预留的 UART 通道（`bus.send("serial*-input")`，基础设施已实证） |

无论落在哪一格都比纯文档状态前进一大步。
