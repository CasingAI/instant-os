# 第五期：类型检查（旁路，不挡运行）

> 建立时间：2026-08-25
> 期次：第五期（依赖第四期落地）
> 涉及项目：`instant-app`（iCode / 生成应用 / 应用包 / VFS）
> 状态：已实施（2026-08-25）
> 前置：`04-第四期-JSX工程.md`（必做）；建议第三期已在，便于把诊断喂给 agent 自修
> 总览：见同目录 `00-总览.md`

目标：在第四期已经能转译、能打单文件的前提下，给工程树补上 **TypeScript 语义检查**。检查在用户浏览器里跑，不上本机 `tsc`。检查失败 **不阻止** 预览转译、不阻止发布打包、不阻止桌面跑已有单文件。诊断给 iCode 预览侧和模型看，用来改源码。

动手时以本文为准。第四期的入口、无安装清单、系统 Preact、开发面多文件 / 发布面单文件，一律不改。本文只加一条旁路检查。

---

## 1. 为什么要有第五期

第四期的打包器只保证模块图能拼上、语法能解析。类型写错、重复的类型声明、组件属性对不上，第四期可以照样打出单文件、照样跑。那是刻意的：先让工程能转、能发。

第五期要把「类型对不对」变成系统能说的话，而不是把运行建立在类型全对上。

---

## 2. 已拍板规则

- **旁路：** 预览和桌面的关键路径仍是第四期。检查结果是附加信号。类型有错，开发面仍按模块转译；用户仍可发布（打包器仍只看模块图）；已发布号的单文件仍按第四期加载。
- **触发：** 不要后台常驻检查服务。一轮草稿写入结束、或用户明确要求时查一次即可。应用树很小，全量可接受。
- **范围：** 只检查当前草稿的源码树（加系统提供的框架类型声明）。不检查产物目录，不把单文件当检查输入。
- **引擎：** 在用户浏览器里跑完整 TypeScript 检查器。优先复用宿主已带的 TypeScript 库（vscode 路径已在浏览器 Worker 里用过它做模块解析）；也可以换成 TypeScript 7 的 WASM 发行，那是同一位置的替换，要求仍是「随网页下发、无本机进程」。不要为了检查再引一套不完整的「轻量检查器」——没有能替代完整类型系统的轻库。
- **框架类型：** 系统把 Preact 的声明提供给检查器，使白名单模块名在检查里也能命中。不要让检查器去网上拉类型包。
- **反馈：** 诊断要落到源文件与行列，预览侧能看见；第三期已在时，模型能读这些诊断并改草稿。
- **不做：** 不把类型错误写成发布门禁；不要求工程里放类型配置文件；不把检查器写进应用包。

---

## 3. 明确不做的事

- 不要改第四期的产物格式、不要发布时因类型错误拒绝打单文件（除非以后另立项做门禁）。
- 不要 Less、不要第三方依赖（那是第六期及更远）。
- 不要本机检查器、不要 CI 式的独立检查流水线。

---

## 4. 建议实施顺序

1. 在浏览器 Worker 里对草稿源码树拉起检查，输出文件级诊断。
2. 注入系统 Preact 声明，白名单模块名在检查中可解析。
3. 预览侧展示诊断；接到第三期 agent。
4. 确认类型全红时第四期预览与发布行为不变。

---

## 5. 验收清单

- 故意写错的类型能在 iCode 里看到指向源文件的诊断；同一草稿预览仍能转译并显示页面（除非同时还犯了第四期会失败的语法/缺文件错误）。
- 带类型错误发布：单文件仍能打出（模块图完整的前提下）；桌面仍跑该单文件。
- 检查器不出现在应用包源码树或产物目录里。
- 「AI 用量」不因检查本身漏接或误计（检查不是模型调用；若某条路径会打模型，另按全局用量规则接线）。
- 号码、草稿、只读、只认最大号，与前几期一致。
