# 第四期：JSX 工程（多文件开发、发布打成单文件）

> 建立时间：2026-08-25
> 期次：第四期（依赖第一期落地）
> 涉及项目：`instant-app`（iCode / 生成应用 / 应用包 / VFS）
> 状态：方案已拍板，未实施
> 前置：`01-第一期.md`（必做）；`02-第二期.md` 与本期正交；建议先做 `03-第三期-AI编辑代理化.md` 再做本期
> 总览：见同目录 `00-总览.md`
> 后续：类型检查见 `05-第五期-类型检查.md`；Less 能否集成见 `06-第六期-Less.md`（探索，不承诺落地）

目标：iCode 管理的应用除了能当静态网站，还能当工程来写：约定入口、标准模块引用、多文件组件、能写 TSX。系统提供 Preact。不要安装清单、不要应用自己选打包器。iCode 里的预览按模块转译、保持多文件形态；发布时在用户浏览器里用 esbuild 的 WASM 版打成一份单文件，写入该正式号文件夹里的约定产物目录；桌面打开正式号只跑这份单文件。

动手时以本文为准。号码、草稿、发布升格、只认最大号、只读正式版，一律仍遵守第一期；治理面仍遵守第二期。本文只改「工程树里写什么、开发面怎么转译、发布时怎么收成可跑的单文件」。

这是本系统自己的开发与发布形态，不依附任何外部前端脚手架。

---

## 1. 为什么要有第四期

第一期把版本做成文件夹、相对引用做成真，但默认仍是普通网页。组件化、拆文件、TSX 都还没有入口。第二期只补历史治理。第三期只换编辑引擎。

第四期要的是：**能当工程写，能写 TSX，发布后桌面有一份收好的单文件可跑。** 模型按组件改草稿；预览转译后立刻能看；用户点发布才打包装进该正式号。

---

## 2. 和第一期网站根的关系

第一期约定：版本文件夹就是网站根，放下就能打开。这对纯网页仍然成立。

TSX 不能直接当网页跑，所以第四期补一条并行规则：

- **静态树：** 找不到工程入口 → 仍按第一期，把该文件夹当网站根加载。旧应用、纯 HTML 应用走这条，不必迁移。
- **工程树：** 找得到工程入口 → 该文件夹是源码工程，外加（正式号上）一份系统写入的单文件产物。预览只认源码树、按模块转译；桌面只认该号里的单文件产物。相对引用、模块名解析都不得逃出这一版的源码树（系统提供的框架库除外；约定产物目录不是源码的一部分，禁止从源码去引用它）。

两种树可以在同一个系统里并存，甚至同一个应用的不同正式号也可以一个是网页、后来一号变成工程。判别只看**这一号文件夹自己**有没有工程入口，不看应用级开关。

---

## 3. 已拍板规则

### 3.1 工程入口与判别

约定入口文件名为 `main.tsx`，放在该版本文件夹根上。版本清单 JSON 也可以写明入口路径（没有则用约定名）。入口存在 → 当工程处理；否则当静态网站根。

入口和「这是不是工程」只靠约定文件 + 可选的清单字段。不要 `package.json`，不要独立构建配置，不要安装清单。

新 iCode 应用默认带该入口和最小骨架（用系统 Preact 挂到页面上）。从商店复制来的纯网页种子仍是静态树。用户或模型之后可以在草稿里补上入口，发布后那一号才变成工程树。

入口与第一期的主网页文件并存时：有工程入口就按工程处理，主网页不参与工程加载。

### 3.2 两套形态：开发面多文件，发布面单文件

同一套源码，两种系统行为：

- **iCode 预览（开发面）：** 只看当前草稿的源码树。系统在用户浏览器里按模块转译 TSX/TS/JSX/JS（剥掉类型、展开 JSX），保持多文件形态交给预览嵌套页加载。不是「不转译」——浏览器跑不了 TSX，只是**不在这一步打成单文件**。不要热替换、不要后台常驻转译服务；草稿树有写入后（第三期建议轮末）刷新预览，刷新时再转一遍。
- **发布（收口）：** 草稿升格为新最大正式号之后，系统在用户浏览器里用 **esbuild 的 WASM 版** 从入口打成**一份**单文件，写入该正式号里约定的产物目录。打包器随宿主静态资源下发，不调用任何人电脑上的本机程序，不起子进程。
- **桌面 / 对外打开：** 只加载当前最大正式号里那份单文件。不再对源码现编。没有这份产物 → 明确失败态，不要假装跑成功，也不要在打开时偷偷补打（补打是发布动作的一部分）。

草稿文件夹里不要求有产物；预览永远不读产物目录。发布后立刻再拷新草稿时，只拷源码树（含清单），不要把产物目录拷进草稿。

### 3.3 源码与产物同夹共存

正式号文件夹里允许同时有：

- **源码树：** 入口、组件、普通样式、图片等，可继续被拷成下一份草稿、被导入导出、被第二期「基于旧档再接一档」拷走。
- **约定产物目录：** 系统在发布时写入的那份单文件。名字留给实现定一个固定目录名，作为保留名：源码不得占用、模块解析不得走进去、编辑器按生成物展示（只读；正式号整棵树本就只读）。

源码仍是下一版怎么改的真相；单文件是这一号怎么跑的真相。二者允许短暂「看起来像同一时刻」，因为产物只在发布那一刻从当时源码打出，正式号随即只读，不会再被改源码而不改产物。

第二期基于某一正式号接出新最大号：整夹拷贝（源码 + 产物 + 该版清单）。新号桌面立刻能跑拷来的那份单文件；内容与源码一致。之后若只改草稿、尚未再发布，桌面仍是该号已有产物。

### 3.4 打包器与运行环境

- 第四期打包/转译用 **esbuild-wasm**，在用户浏览器里运行。本机 esbuild 二进制禁止用于这条链路。
- 工程用模块名引用框架（以及配套钩子、JSX 运行时），由系统解析到内置的那一份，打进转译结果或单文件。不要把框架文件拷进每个应用包。
- 嵌套页里的微应用和宿主不是同一套运行时：微应用用系统供给它的那一份，不要去复用宿主自己正在用的实例。
- 第四期只提供这一套框架。不要同时塞别的框架，也不要让应用自带一份和系统抢解析。
- 裸名白名单本期钉死为：`preact`、`preact/hooks`、`preact/jsx-runtime`。其它裸名一律解析失败。JSX 用自动运行时（不必每个文件手写工厂函数）。
- 相对路径按常见 TypeScript 习惯补全扩展名与目录入口文件；解析不得逃出该版本源码树。

### 3.5 语言与样式（本期范围）

- 可以写 `.tsx` / `.ts` / `.jsx` / `.js`。转译剥掉类型，**不做类型检查**（见 `05-第五期-类型检查.md`）。类型写错不阻止预览转译和发布打包——打包只保证模块图能闭合、语法能解析。
- 样式本期只要求 **普通 CSS**：可作独立文件、可从模块里引用；发布时打进那份单文件（样式内联进该文件，桌面仍只加载一个文件）。不要 Less、不要样式模块化方案、不要其它预处理器（见 `06-第六期-Less.md`）。
- 图片等静态资源：解析不得逃出源码树；发布时由打包器收进单文件（例如内联）。预览侧同等约束，不得靠外网地址凑资源。

### 3.6 默认生成

新从 iCode 创建的应用，按 TSX 工程生成（约定入口 + 最小骨架 + 引用系统 Preact）。不要再把「整份内联网页」当新应用的默认。

已存在的静态树不自动改写。第一期迁过来的旧内部项目仍是网页，直到有人在草稿里改成工程并发布。

### 3.7 发布、运行、治理

- 发布仍是草稿升格为新最大号并只读，立刻再拷新草稿（只拷源码）。升格之后立刻打单文件写入该号产物目录；打包失败则这一号不能当作桌面可运行（明确失败；不要留下半截当成功）。
- 桌面仍只认最大正式号；名字、图标、颜色、能力仍读最大号那份清单。
- 用户数据跨版本共用；聊天仍在版本树外。

### 3.8 导入导出

整包带走：源码、产物（若该号已有）、清单、以及第一期已规定的聊天与用户数据。导入端桌面打开工程号时跑带过来的单文件，不要求导入端当场再打一次。两边都具备第四期能力时，打开 iCode 应能看到同一棵源码工程，预览按模块转译草稿（或按「确保草稿」从最大号源码拷出后再转）。

## 4. 仍遵守的第一、二期规则

- 身份、最大正式号、草稿只写、正式版只读、文件管理器不准删正式版。
- 网站根那条对静态树仍然适用；工程树源码的等价约束是「模块与资源解析不逃出该版本源码树」。
- 无入口：静态树无主网页 → 空白页；工程树无约定入口也无清单入口 → 当静态树处理，再按有无主网页决定空白或网页。
- 不要把聊天或开发状态放进工程树当可被页面请求的资源。

## 5. 明确不做的事

- 不要第三方依赖、不要包安装、不要生成应用运行时的终端工作流（第三期 iCode 开发面的 agent 终端不在此列）。
- 不要完整打包配置、不要应用自己选打包器、不要 `package.json`。
- 不要类型检查（第五期）。
- 不要 Less 及其它 CSS 预处理器（是否能做、做不做进产品，见 `06-第六期-Less.md`；本期当不存在）。
- 不要强制把旧的纯网页应用改写成工程。
- 不要让微应用复用宿主的框架实例。
- 不要改号码规则、不要分支、不要运行指针、不要改商店更新流水线。
- 不要热替换、不要后台常驻转译服务。
- 不要在打开桌面应用时现编源码来代替产物；缺产物就是失败。
- 不要把本机 esbuild / tsc 当成发布或预览链路的一部分。

## 6. 建议实施顺序

按依赖往下做。不要和第一期的静态加载、第二期的治理面搅成一次大改。

1. **判别与加载分叉：** 有工程入口则走工程，否则走第一期网站根。验收：旧网页应用行为不变。
2. **浏览器内 esbuild-wasm：** 能从虚拟文件树读源码（插件拦截解析/加载，因 WASM 没有磁盘）。
3. **开发面按模块转译：** 草稿预览能跑入口 + 子组件相对引用；逃出源码树失败；写入后刷新预览。
4. **系统解析框架模块名：** 白名单内的 Preact 相关名字能解析，包内不必自带框架文件。
5. **发布打单文件：** 升格后写入产物目录；桌面只跑单文件；样式与资源收进该文件。
6. **新应用默认骨架：** 创建即是工程；未发布前桌面仍是上一档（静态树或旧产物）。
7. **生成与编辑：** 模型默认按 TSX 工程改源码（走第三期 agent）；预览转译失败可见，模型能读报错自修。
8. **和治理、导入导出对齐：** 基于旧工程档接出的新最大号带源码也带产物、桌面能跑；导出再导入后源码与产物都在。

---

## 7. 验收清单

- 新 iCode 应用是 TSX 工程：预览按模块转译后能看见骨架；能引用系统 Preact，包内没有一份自带的框架拷贝。
- 能新增组件文件并用相对路径引用；预览能到。引用逃出该版本源码树失败。
- 草稿写入并刷新后预览反映源码；未发布前桌面仍是上一档正式号的跑法（网页根或已有单文件）。
- 发布后：新最大号里同时有源码树和单文件产物；桌面打开只跑该单文件，不现编源码。
- 发布打包失败时不要把该号当成桌面成功页；预览转译失败时预览能看见原因。
- 新草稿没有产物目录；预览不读产物。
- 第一期风格的纯网页应用（无工程入口）预览和桌面仍按网站根工作。
- 同一应用可以先作为网页发布、再在后续正式号变成工程；判别按那一号文件夹。
- 基于某一工程正式号接出新最大号后，新号带源码也带产物，桌面跑拷来的单文件。
- 导入导出带源码也带已有产物。
- 全程没有包安装、没有应用级打包配置、没有类型检查要求、没有 Less；生成应用运行时没有终端。
- 号码、草稿、只读、只认最大号、用户数据与聊天位置，与第一、二期一致。
