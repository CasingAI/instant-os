# 第三期：iCode 编辑代理化（SEARCH/REPLACE 换 Agent 框架）

> 建立时间：2026-08-25
> 期次：第三期（依赖第一期落地）
> 涉及项目：`instant-app`（iCode / 生成应用 / 应用包 / VFS / vscode AI 框架）
> 状态：方案已拍板，未实施
> 前置：`01-第一期.md`（必做）；`02-第二期.md` 与本期正交；本期与 `04-第四期-JSX工程.md` 正交，但强烈建议先做本期再做第四期
> 总览：见同目录 `00-总览.md`

目标：把 iCode 的编辑引擎从「单发流式 SEARCH/REPLACE」整体替换为系统已有的 Agent 框架（vscode AI 那套）：模型通过工具循环操作终端、按路径读写草稿树文件，改完即预览。能力请求改为独立工具。写入硬限当前草稿文件夹，读取放开。AI 用量照常计入统计。生成应用本身仍然不带终端——终端只是 iCode 开发面的基础设施。

动手时以本文为准。号码、草稿、发布、只认最大号、只读正式版，一律仍遵守第一期；治理面仍遵守第二期。本文只改「iCode 里模型怎么改草稿」，不改一棵版本树里放什么。

---

## 1. 为什么要有第三期

### 1.1 现在的编辑方式

iCode 目前的编辑是单轮流式补丁：模型在一条回复里输出 Aider 风格块，前端逐块解析后对整份源码字符串做「逐字精确、全文唯一」匹配替换：

- 块格式无路径字段（历史上只有一份 HTML），第一期多文件后必须扩展成逐文件寻址；
- SEARCH 匹配失败只能报错进 `failedEdits`，模型没有机会看到失败并自修；
- 改完无法验证——不跑编译/预览检查，错了要等用户发现再开新一轮；
- 能力门禁织在输出格式规则里（未授权时禁止输出代码），与内容生成强耦合。

### 1.2 系统里已有的东西

vscode 应用的 AI 面已经是一套完整 Agent 框架，且已被 ProDude 复用验证过第二个消费者可行：

- 工具循环（步数上限、上下文压缩、Sub Agent、模式切换）；
- `run_in_terminal`：受控 InstantREPL（QuickJS）终端，模型用 `fs.readFileSync/writeFileSync` 等直接读写 VFS；
- 受控终端 changeset 日志 + 整轮回滚（`revert_terminal_changes`），比 SEARCH 失败仅报错强一档；
- 终端输出超限自动 spill 落盘、分段读取。

第三期要做的不是发明新机制，而是给 iCode 接上这套现成引擎，并砍掉旧引擎。

## 2. 已拍板规则

### 2.1 替换，不并存

- iCode 聊天的代码修改**整体换成 agent 循环**。删除 SEARCH/REPLACE 块的解析、应用、展示链路（解析器、流式 feed、对话区内联渲染旧/新代码标签等）。
- 对话区从「内联渲染补丁块」改为活动时间线（工具调用卡片：意图短句 + 可展开的命令/结果），沿用 vscode AI 面的既有组件形态。
- 不保留「旧格式开关」或双轨期。旧聊天记录里已存的 SEARCH/REPLACE 文本作为历史原文只读保留，不再解析执行。
- 预览刷新粒度随之改变：从流式逐块变为每轮写操作后刷新。监听草稿树文件变更触发即可，不要做定时轮询。

### 2.2 引擎与宿主

- 复用 `askVscodeAgent` 及其工具集（`createVscodeAiTools`）的 agent 形态；iCode 作为第三个消费者提供自己的 host 与上下文构建，不为 iCode 另起一套循环实现。
- iCode 场景的工作区就是该应用的草稿文件夹树；上下文注入改为草稿树的文件清单 + 当前打开文件，不再注入整份 HTML 源码。
- 模型改文件走终端脚本读写 VFS；不新增专用 write_file/edit 类工具（终端即文件操作是本框架的既有约定，保持一致）。

### 2.3 能力请求改为独立工具

- 能力请求从「输出格式禁令」改为**独立 tool**：模型在需要未授予能力时调用该工具发起请求，用户授予后 agent 继续；拒绝则模型收到明确反馈继续干活或收尾。
- 未授权状态下不再用提示词禁止模型产出代码——门禁移到工具层与运行时层（嵌套页能力桥照旧拦截）。
- 现有 REQUEST_CAPABILITY 块格式随 SEARCH/REPLACE 一同退役。

### 2.4 读写边界

- **写入硬限当前草稿文件夹**：所有写操作的目标路径必须在 `Draft/` 树内。工具层做路径前缀限定；VFS 节点属性兜底（正式版天然只读，绕过工具直接写也会被拒）。
- **读取放开**：模型可以读工作区里其它文件作参考（单用户本地系统，文件管理器本来就看得见全部 VFS，读没有额外信任边界）。不为此做强制拦截。
- 提示词层面约定卫生习惯（别翻 `Data`、别在无关目录浪费步骤），但不做硬性读取白名单。

### 2.5 AI 用量统计必须接线

- iCode 现在自己直连 OpenAI 并显式记录用量；换到 agent 后必须走框架暴露的 usageContext 接线（run-agent 层已支持）。漏接不会报错、只会静默不出现在「AI 用量」面板——这是验收项，不是可选项。

### 2.6 边界声明（与第四期的关系）

- 本期的终端是 **iCode 开发面基础设施**：agent 操作草稿用，不进版本树，不是生成应用运行时的一部分。
- 第四期「不上终端」指的是**生成应用本身**不带终端工作流、不装包。两者不冲突：应用跑起来没有终端；开发者（模型）在 iCode 里用系统终端改源码。
- 本期不做 TSX、不上转译/打包。第四期落地后，同一套 agent 能读预览转译报错并自修；类型诊断是第五期，Less 报错是第六期。

## 3. 仍遵守的第一、二期规则

- 号码、最大正式号、草稿只写、正式版只读、文件管理器不准删正式版，全部不变。
- 聊天仍在版本树外、绑在应用上；用户数据跨版本共用。
- agent 的存在不改变发布语义：改的是草稿，发布仍是升格新最大号。
- 第二期的治理动作（看/删非最大号/基于旧档接新号）不受影响。

---

## 4. 明确不做的事

- 不要保留 SEARCH/REPLACE 作为回退通道或可选模式。
- 不要为 iCode 重写一个平行 agent 循环；复用 vscode AI 框架的循环与工具协议。
- 不要给模型开放草稿树之外的写权限，也不要为读做强制沙箱。
- 不要在本期引入 TSX、转译/打包、包安装——那些属于第四期及以后。
- 不要让 agent 触碰发布动作（升格、删档、基于旧档新建都是用户在治理面点的，模型不代劳）。
- 不要改变聊天存储位置或把聊天迁进草稿树。

---

## 5. 建议实施顺序

1. **接线：** iCode 聊天挂上 agent 循环与终端工具，作用域限草稿树；用量接线完成并在「AI 用量」可见。
2. **能力工具化：** REQUEST_CAPABILITY 改独立工具，删旧格式禁令提示词。
3. **UI 切换：** 对话区改活动时间线；预览改为文件变更驱动刷新。
4. **拆除旧引擎：** 删 SEARCH/REPLACE 解析、应用、展示链路及相关提示词；迁移提示词中仍有效的部分（如中文回复、简洁说明改动）进 agent system prompt。

---

## 6. 验收清单

- 用户在 iCode 里提修改需求，模型经工具循环直接改草稿树内文件，预览反映新内容；全程对话区看不到 SEARCH/REPLACE 块。
- 模型尝试写草稿树之外路径时被拒且能收到错误自行纠正；正式版文件夹任何情况下不可写。
- 模型可以读取其它路径作参考（例如参考别的应用源码），不被拦截。
- 需要未授予能力时，模型调用能力请求工具弹确认；拒绝后模型不产出依赖该能力的代码或给出替代说明。
- 一轮里多次写操作可整轮回滚。
- 「AI 用量」面板能看到本次编辑消耗的 token；不因换引擎而丢失统计。
- 旧聊天记录中的历史补丁文本原样可读、不再被执行。
- 发布、治理、导入导出行为与本期内置前后一致；版本树里没有任何 agent 或终端痕迹。
