# 第十一期：运行时宿主 syscall hook

> 建立时间：2026-08-26
> 期次：第十一期（QuickJS / Instant Node 运行时层；与第十二期解耦）
> 涉及项目：`instant-app`（quickjs 实例 / 终端 REPL / iCode agent 终端 / Produde / Virtual JS / instant-shell）
> 状态：未实施
> 前置：无（运行时基建；不依赖第八期）
> 后续：第九期（第一个真实使用方：写时并发检查拦截器）
> 与第十期正交（github-desktop 不走 QuickJS）

目标：给 Instant Node 运行时加一层**跨沙箱调用**的拦截链。沙箱里的脚本无论调文件、网络还是终端内置壳层，只要真正离开沙箱、打到宿主，都经过同一套「调用前 / 调用后 / 失败」钩子。钩子**按实例在创建时挂上**，不按全局改运行时源码。第九期的「写时并发检查」只是这条链上的第一个使用方；以后加审计、二次确认、限额，都只写拦截器，不再为每个功能去改各内建模块。

## 1. 为什么要有第十一期

### 1.1 现状：没有统一出入口

Instant Node 不是真 Node。终端、iCode agent、Produde、Virtual JS、包安装脚本，底层都是同一个「创建 QuickJS 实例」的入口。实例创建时，把一堆内建能力分别注进去：文件、网络、加密、压缩、定时器、终端壳层、webview……每一个都自己把宿主函数绑到沙箱里。

结果是：

- 想给「写文件」加前置检查，就得改文件桥
- 想给「联网」加审计，就得改网络桥
- 想给「终端壳层命令」加确认，就得改壳层注入
- 每加一种策略，就在对应模块里再挖一次

这就是「为每一个功能单独修改 Node 运行时」。

已经存在的策略，其实都堆在实例这一层，只是写死的：读写根、写拒绝前缀、单文件大小上限、受控模式的变更日记、网络开关、可选的壳层 / webview 宿主。它们证明**策略属于实例，不属于存储层**。本期要把「写死的策略」收成「创建实例时挂上的拦截链」。

### 1.2 为什么不是文件系统公开 API

若把钩子挂在文件系统的公开写入口上：

- 只有走这条写入口的人受益，网络 / 壳层 / 其它内建完全摸不到——正是这次顾虑
- 更糟：若钩子在写前现读版本、再把「此刻的版本」填成期望值，校验永远对着刚读到的值，等于没校验。用户在 agent 思考期间改的文件，照样被覆盖
- 文件管理器保存、商店同步、github-desktop 拉代码，和 agent 写草稿会被同一条全局钩子一视同仁。调用方无法选择「我要不要这套策略」
- github-desktop 根本不经过沙箱，挂在文件系统入口上既拦不住它真正在意的路径，又可能误伤它

文件系统公开 API 只适合提供**原语**（第八期：写时可以带上「我期望的版本」）。「什么时候带、带哪一次读到的版本」是运行时策略，必须能区分「这个实例是 agent」还是「这个实例是用户自己敲的 REPL」。

### 1.3 为什么不是「终端 App」

日常说的「终端」有两层：

- 上面：终端窗口 / InstantREPL 面板（UI）
- 下面：面板创建出来的 Instant Node 实例（真正执行脚本、注入内建的地方）

iCode agent、Produde 用的是隐藏挂着的同一类实例，不是用户看得见的那个终端窗口。Virtual JS、开机启动项、包安装脚本也创建同类实例，但它们不是终端 App。

所以拦截点是**创建 Instant Node 实例时**，不是终端 UI。这样：用户终端、agent 终端、其它脚本运行器都能挂；UI 层零感知。

### 1.4 拦什么、不拦什么

拦的是**跨沙箱调用**：沙箱自己算不出来、必须问宿主的那些事。

拦：

- 文件：读 / 写 / 追加 / 流式写 / 删 / 改名 / 建目录 / 看状态……一切会碰到 VFS 的
- 网络：宿主侧的 fetch
- 终端壳层：`instant.*` 那套宿主命令（含 git 等）
- 已注入的 webview 宿主绑定（若该实例有）

不拦（纯计算 / 沙箱内）：

- 路径拼接、缓冲区、事件、断言、计时器、流的纯变换、压缩算法本身（若压缩已在沙箱内完成、只在读写文件时才出沙箱，则只在文件那一跳出拦）

原则：钩子看到的是「系统调用名 + 已从沙箱解出来的参数」，不是沙箱句柄。解参数仍由各内建模块做；钩子不解析沙箱内部对象。

## 2. 已拍板规则

### 2.1 按实例挂，不按进程全局挂

创建实例时传入拦截器列表。该实例上每一次跨沙箱调用都走这份列表。实例销毁，链一起没。

不同创建点可以挂不同的链：

- iCode agent 用的实例：挂「记上次读到的版本、写时带上期望版本」
- 用户自己开的终端：默认不挂这条（用户敲写文件就是要写）
- Virtual JS / 包安装：默认不挂
- 以后若要全终端审计：在终端面板创建实例的那一处加审计拦截器，不必改运行时内部

这就是「在调用它的地方使用 hook」，而不是「改 Node 运行时源码」。

### 2.2 一条链、三个时机

每个拦截器可提供：

- 调用前：可改即将交给真正实现的参数（例如给写操作补上期望版本）；可抛错直接拒绝（沙箱看到和实现层失败一样的错误）
- 调用后：看到成功结果（例如读文件成功后把该路径的版本记下来）
- 失败时：可观察；**不吞掉**未预期的异常，继续冒泡

链按注册顺序执行。调用前整条跑完才进真正实现；真正实现失败则走失败时机，再抛给沙箱。

拦截器自己挂了（抛了不是业务拒绝的错）：**不吞**，顶层按运行时既有错误通道报出来。

### 2.3 系统调用要有稳定名字

名字按「域.动作」，例如文件写、文件读、文件追加、网络请求、壳层某条命令。各内建模块在绑宿主函数时声明自己的名字；拦截器按名字过滤（精确或按域前缀）。本期要把**文件全套、网络、壳层**都接上名字并走链——不是先只接文件、其它以后再说。纯计算内建不接。

### 2.4 运行时提供包装，各内建改用包装，不改业务

本期要动的是「宿主函数怎么绑上去」：各内建不再直接把实现暴露给沙箱，而是经过运行时提供的包装再暴露。文件桥里「先看状态再决定创建还是覆盖」这类业务逻辑**不动**；网络、壳层的业务逻辑也**不动**。只是出沙箱的那一跳套上链。

文件桥里已经有的读写根检查、大小上限、受控模式日记，**先保持原样**（仍在实现内部）。本期不把它们重写成拦截器——避免一次把权限模型掀翻。它们和用户拦截器的关系：先跑用户链的调用前，再进实现（实现里仍做权限 / 日记）。若调用前已经拒绝，实现根本不会跑。

### 2.5 和第八期的边界

- 第八期：存储原语。写的时候可以带「我期望的版本」，不等就拒。不感知 agent，不感知实例。
- 第十一期：策略通道。不实现「版本是否匹配」本身。
- 第九期：用本通道，在具体实例上记住「上次读到的版本」，写的时候把期望版本填进第八期的原语。

本期**可以先于第八期落地**（链先空跑，行为与现一致）。第九期必须两期都齐。

### 2.6 性能与可观测

跨沙箱调用不是热路径（相对纯计算）。链上多几次异步检查可以接受，但拦截器必须自己短路：名字不匹配立刻返回。运行时不给拦截器做隐式缓存。

调试：系统调试日志已有文件宿主追踪；链的进入 / 拒绝可复用同一通道，但本期不强制做新的可视化面板。

## 3. 验收清单

- 创建实例时可传入拦截器列表；不传则行为与现完全一致（所有现有终端 / Virtual JS / 包安装 / 测试仍绿）。
- 文件、网络、壳层三类跨沙箱调用都会进链；拦截器能按名字区分。
- 调用前抛错 → 沙箱侧看到失败，真正的文件 / 网络 / 壳层实现未执行。
- 调用前改写参数 → 真正实现看到的是改写后的参数（第九期靠这个补期望版本）。
- 调用后能看到成功结果（第九期靠这个更新「上次读到的版本」）。
- 两个实例互不影响：A 挂了拦截器，B 没挂，B 的写不被 A 的策略挡住。
- 实例销毁后，其拦截器不再被调用（无悬挂）。
- 纯计算内建（路径、缓冲区等）不进链。
- 现有读写根、网络开关、受控模式日记行为不变。

## 4. 明确不做的事

- 不在文件系统公开 API 上做全局钩子。
- 不把钩子做成沙箱内的对象代理（可被绕过，且看不到真正出沙箱的那一跳）。
- 不在本期实现写时并发检查（那是第九期）。
- 不把已有权限 / 日记重写成拦截器。
- 不拦纯计算内建。
- 不做进程级默认拦截器列表（避免「一挂全中」）。
- 不改 github-desktop（它不创建 Instant Node 实例）。

## 5. 建议实施顺序

1. 在创建实例的选项上增加拦截器列表；运行时提供「按名字调用前 / 后 / 失败」的包装。
2. 文件宿主那一整组出沙箱实现改走包装（这是最密的一域，也是第九期要用的）。
3. 网络宿主、壳层宿主同样改走包装（兑现「任意内置、现在就能挂」）。
4. 测：空链回归；按实例隔离；调用前拒绝；调用前改参；名字过滤。
5. 现有沙箱 / 终端 / 受控模式 / 网络权限的测试保持绿。
