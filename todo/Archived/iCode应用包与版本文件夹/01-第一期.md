# 第一期：从注册表整包 JSON 迁到应用包版本文件夹

> 建立时间：2026-08-25
> 期次：第一期（已拍板；后续期次见同目录）
> 涉及项目：`instant-app`（iCode / 生成应用 / 应用包 / VFS）
> 状态：已实施（2026-08-25）
> 总览：见同目录 `00-总览.md`

目标：iCode 不再把内部项目（源码、元数据、聊天、预览键值）整包塞进应用注册表。每个 iCode 程序就是系统里的一个生成应用，源码和资源按版本落在应用包的文件夹树里。桌面只运行当前最大正式版；iCode 只编辑草稿；发布把草稿升格成新的最大正式号。每个版本是一棵可被当作网站根打开的文件树，相对引用必须能在这棵树里解析。

本文是已讨论拍板的产品与结构约束。动手时以本文为准；与旧实现冲突时改实现，不另起一套平行身份长期并存。

---

## 1. 为什么要改

### 1.1 现在的别扭

系统里已经有「生成应用」：桌面图标、应用包、版本快照、运行时键值、能力标签。iCode 却还维持一份平行的「内部项目」清单，整份项目列表写成注册表里的一个 JSON 字段。每个项目把名称、整份网页源码、聊天、预览用键值揉在一起；改其中一个项目会把整份列表写回去。

创建项目时已经会在桌面挂占位入口，发布也是往这份生成应用上写。真正的问题是身份拆成两份：编辑真相在 iCode 的大 JSON 里，桌面入口是另一份应用。「发布到桌面」目前还只是覆盖当前快照，并不切新版本。应用商店那条线才会追加版本，而且回滚是砍掉最新一截，不是切换「最大号」。

单文件网页也已经落后：脚本、样式、图片无法作为邻居文件存在，因为运行时并不是按目录打开，而是把一份网页整段塞进嵌套页。

### 1.2 第一期要得到什么

1. **一个程序 = 一个系统应用。** iCode 只是它的开发面，不再自带平行项目数据库。
2. **版本 = 子文件夹。** 正式版用正整数文件夹名（`1`、`2`、`3` …）；草稿用固定名 `Draft`，扫描最大正式号时排除。
3. **运行只认最大正式号。** 桌面图标、对外名字、图标、颜色、能力，一律读当前最大正式版文件夹里的那份清单。草稿再怎么改都不漏到桌面。
4. **iCode 只改草稿。** 打开某应用时若没有草稿，从当前最大正式版拷一棵。发布把草稿变成新的最大号并只读，然后立刻再拷一棵新草稿让当前窗口继续改。
5. **每个版本是网站根。** 预览跑草稿这棵树，桌面跑最大正式版这棵树。页内相对引用只在这棵树里解析，出不去。没入口则空白页。
6. **用户数据跨版本共用。** 聊天绑在应用上，放在版本树外面，不进网站根。
7. **多文件 = 静态网站，不是工程。** 主网页可以引用同树里的脚本、样式、图片。默认仍是 HTML/CSS/JS。第一期不用 Preact，不上构建链。

## 2. 现状（改之前）

| 项 | 现在 |
|---|---|
| iCode 内部项目 | 注册表命名空间 `icode`，字段 `projects`（更早从 localStorage / 单键 `store` 迁来），整列表一个 JSON |
| 项目内容 | 元数据 + 整份 HTML + 键值快照 + 聊天，全在同一对象里 |
| 桌面身份 | 创建时 `syncAppFromIcode` 写占位生成应用；`linkedAppId` 把内部项目和 `gen:` 应用拴在一起 |
| 保存草稿 | 只写内部项目，不改桌面正在跑的网页 |
| 发布到桌面 | 仍走同步覆盖最新快照，**不追加版本号** |
| 生成应用本体 | `/Applications/{包名}/Contents/`：清单 + 每版本一个网页文件（如按版本号命名的 html） |
| 版本模型 | 快照栈，最后一项为当前；应用商店更新会追加；回滚删除栈顶 |
| 运行时键值 | 生成应用注册表，按键拆开；与内部项目里的 `appData` 重复 |
| 运行加载 | 把整份 HTML 灌进嵌套页（同源写入或 Blob 地址），相对路径对不上包内邻居文件 |
| 文件管理器 | 应用包 `Contents` 对用户只读，系统层可写；`Data` 是应用数据目录 |
| 生成目标 | 模型按单份 HTML 做 SEARCH/REPLACE；样式规定内联 |

涉及模块（改动时以这些为锚，不要再平行搞一套「内部项目」长期并存）：

- iCode：存储、发布/同步、备份导入导出、编辑器主界面、预览准备、生成补丁规则
- 生成应用：已安装列表与同步、应用包 Contents 读写、运行时嵌套页与各类桥
- 文件系统：应用程序卷、包目录、节点只读/可写属性
- 设置里的生成应用体积 / 历史版本清理（语义要跟新文件夹模型对齐，第一期不必做完所有清理 UI）

## 3. 目标包结构

每个 iCode 管理的生成应用是应用程序卷上的一个包。建议形态：

```
/Applications/{包名}.app/
  Versions/
    1/                 正式版，只读
      （该版本清单 JSON）
      index.html       入口约定；没有则运行/预览为空白页
      …其余文件与子目录（该版本网站根）
    2/
    Draft/             草稿，可写；不参与「最大正式号」扫描
  Data/                运行时用户数据，跨版本共用（沿用现有应用数据目录）
  Developer/           开发附属：聊天等；不是网站根，运行时不得当资源提供
```

与现有 `Contents` 里「每版本一个网页文件」的关系：**换成每版本一个文件夹**。包级若仍需要一份极轻的索引（应用 id、iCode 管理标记），可以留在包根或旧 Contents 位置，但**名字、图标、颜色、能力不放在包级一份里**，而放在每个版本自己的清单 JSON 里。桌面读最大正式版那一份。

整数文件夹名只承认正整数（`1`、`2`、`3`）。`Draft` 是保留名。不要用负数或更小的版本号冒充草稿：删光正式版或尚未发布时，草稿会变成「最大号」，桌面会跑到编辑副本。

旧的语义化版本字串（商店那套）不搬进 iCode 的整数文件夹规则。iCode 管理的包只走整数号。

## 4. 已拍板规则

### 4.1 身份

- 不再维持「内部项目 / 正式应用」两套清单。iCode 首页**只列从 iCode 建立的应用**（含从商店复制出来、已改由 iCode 管理的副本）。
- 创建即对应一个生成应用包。没有正式版、没有正式内容时，桌面仍可打开，沿用现在对空/占位应用的处理；**不要把草稿当成最大正式号来跑**。
- 应用商店原应用保持老机制，**不能在 iCode 里直接改**。只能复制成新身份的 iCode 应用，之后用 iCode 自己的版本规则更新。

### 4.2 最大正式号

- 扫描 `Versions` 下正整数文件夹，取数字最大者。没有则「无正式版」。
- 桌面运行、桌面图标、启动器上的名字 / 图标 / 颜色 / 能力，只看最大正式版文件夹里的清单 JSON。
- 草稿不是最大正式号，改草稿不得泄漏到桌面。问「草稿改名桌面要不要变」没有意义。

### 4.3 草稿与发布

- iCode **只能修改 `Draft`**。
- **只要 iCode 打开着这个应用，就必须有一棵可写草稿。** 没有则从当前最大正式版拷一棵；没有正式版则从空模板 / 现有占位内容起一棵草稿（仍不把它变成正式号）。
- **发布：** 把当前草稿升格为 `max+1`（尚无正式版则为 `1`），该文件夹改为只读。然后立刻再从这份新正式版拷一棵 `Draft`，当前 iCode 窗口切到新草稿继续改。
- 升格用「拷到新文件夹再处理旧草稿」，避免只改名导致中途失败后既没有草稿也没有正式版。实现上要保证：成功后旧 `Draft` 不再作为可写工作区留下一份脏副本与新 `Draft` 打架。
- 关掉 iCode 时可以没有草稿（刚发布完就关、或导入的包里本来就没有）。下次打开再从最大号拷——和「打开时确保草稿」是同一条规则。
- **不要热修复当前正式版、不切新号。** iCode 里已有预览。每次发布都是新的最大号。旧正式版第一期先留着；看列表、删旧档、基于旧档再接新最大号见 `02-第二期.md`。

### 4.4 只读与文件管理器

- 正式版文件夹：发布后设为只读（VFS 已有可读/可写属性则用它）。
- 文件管理器**不允许删除正式版文件夹**（包括当前最大号）。iCode 里删非最大号见第二期。
- 草稿可写；用户在文件管理器里改草稿可以允许（仍是草稿，不影响桌面）。正式版不可写。

### 4.5 每版本一份 JSON

每个版本文件夹内有一份清单，至少包括：名字、图标、颜色、能力标签。描述、分类一并放进这份 JSON（同属「这个版本是谁」）。桌面只读最大号那一份。

能力标签随版本走：预览按草稿的 JSON 解释需要什么能力；桌面按最大正式版的 JSON。系统侧授予仍按应用，不按版本拆授权表（草稿若新用了尚未授予的能力，走 iCode 现有的能力请求；发布后最大号 JSON 带上新标签）。

### 4.6 运行时数据与聊天

- **用户数据跨版本共用。** 仍走现有应用数据（注册表键值 + 包内 `Data`），不按版本各做一份。升版本不清空用户数据。
- **聊天绑在应用上，物理位置在版本树之外**（如包内 `Developer`）。不进 `1/`、`2/`、`Draft/`，以免被当成网站资源、或随升格变成只读站点的一部分。
- 发布不重置聊天。从最大号拷草稿只拷网站根和该版清单，不把聊天复制进草稿文件夹。
- 以后若要从很老的正式版开一棵草稿，聊天仍是后来的上下文——那是后续问题；第一期不按版本拆对话。

### 4.7 网站根、相对引用、多文件

资源文件跟着版本文件夹走，不另存一套。

打开某个版本时，**这一棵文件夹就是网站根**：

- 桌面：最大正式版那棵树。
- iCode 预览：`Draft` 那棵树。
- 入口约定为主网页（`index.html`）。没有入口 → 空白页，不算崩溃。
- 页内相对引用（同目录脚本、样式、图片、子目录）必须在这棵树里解析成功。
- 解析不得逃出该版本文件夹（不能读到兄弟版本、`Data`、`Developer`、其它应用）。

现在把整份 HTML 灌进嵌套页的方式**不够**，必须改成「按目录提供文件」。这是第一期不可砍掉的部分：只把文件存进版本文件夹、跑起来仍是单文件，等于多文件是假的。不要求做通用网站服务器，只要求该树内部的相对引用可用。

**第一期要的多文件：** 能拆开的静态网站。主网页仍是默认生成物；样式、脚本、图片可以是邻居文件。编辑器能看见草稿树、能打开并保存其中具体文件；模型允许按路径改文件。

**第一期不要的多文件：** 依赖安装、打包、多入口工程、终端工作流。也不要把微应用默认改成 Preact/JSX：宿主用 Preact 和嵌套页里的微应用不是同一套运行时；第一期不上构建链、不规定从系统注入框架。JSX 工程化见 `04-第四期-JSX工程.md`，不要提前做。

### 4.8 从应用商店复制

- 原商店应用不动，不能在 iCode 里改它。
- 复制出**新身份**的 iCode 应用。
- **不带**商店历史版本、不带用户数据、不带已授能力。
- 只把**当前正在跑的那一版**当种子，写成新包的正式版 `1`（这样新图标立刻能跑拷来的内容，而不是占位页）。打开 iCode 再从 `1` 拷 `Draft`。
- 桌面上会同时有商店原版和 iCode 副本两个图标。

### 4.9 导入导出

- 能带的都带：全部正式版、当时若存在的草稿、聊天、用户数据、每版本清单。导入到另一台设备后，打开 iCode 应看到与导出端当时相同的东西。
- 导出是文件系统状态的快照：若导出端刚发布、还没有草稿，导入端也没有草稿；对方打开 iCode 时再按「确保草稿」从最大号拷。
- 目标机已有同一应用或同名应用：**做成副本**（新身份、新名字，沿用现有「副本」后缀规则），内容仍整包带上。

## 5. 第一期明确不做的事

- 不要每保存就加一个正式号。
- 不要「钉在某一旧版运行、同时保留更大号」。运行永远最大正式号。第一期不做指针、也不在 iCode 里删正式版；第二期用「基于旧档接出新最大号」回到旧内容，而不是删掉当前最大号。
- 不要覆盖当前正式版的热修复通道。
- 不要把聊天或开发状态放进网站根。
- 不要在 iCode 里直接改商店原应用。
- 不要把应用商店的更新流水线改成 iCode 这套整数文件夹（商店继续老机制）。
- 不要做分支、并行多份草稿、语义化版本号、版本间 diff、按版本拆用户数据。
- 不要做从任意旧版「升格回最大号」的完整界面；iCode 只动草稿。数据模型不要堵死以后「把旧正式版拷进草稿再发布成新最大号」。
- 不要把 iCode 首页扩成「所有已安装生成应用都能打开编辑」。
- 不要把微应用默认生成改成 Preact/JSX，不要为微应用做打包/转译链。那是 `04-第四期-JSX工程.md`。
- 不要做完整工程体验（依赖、构建、终端工作流）。第四期是「TSX 工程 + 预览按模块转译 + 发布写入单文件」；类型检查是第五期，Less 是第六期。更长的「以后」清单见 `00-总览.md`。
- 不要在第一期做版本列表、删旧正式版、基于旧档新建最大号。那是 `02-第二期.md`。第一期只保证正式版只读、文件管理器删不掉；堆着即可。

## 6. 迁移

旧内部项目一次性迁完，不要双写很久。

建议对应关系：

- 每个内部项目 → 一个 iCode 管理的生成应用包（已有 `linkedAppId` 的用原应用身份，避免桌面图标分裂）。
- 当时已发布到桌面的网页 → 正式版 `1`（若已有多份生成应用版本快照，按时间/原版本顺序变成 `1`、`2`、`3`…，当前桌面在用的那份成为最大号）。
- 内部项目里尚未发布的源码 → `Draft`。若与最大正式版相同，仍应有一棵草稿（打开 iCode 就会需要）；也可迁完不写草稿，第一次打开再拷。
- 聊天 → 包内开发目录，不进版本树。
- 运行时键值以桌面上那份注册表 / `Data` 为准（两边现在是重复的）；不要用内部项目里的旧快照覆盖正在用的用户数据。
- 迁完删除 iCode 注册表里的项目列表字段，首页改为枚举「带 iCode 管理标记的生成应用」。

商店来的、从未被 iCode 管理的应用：不自动改成整数版本文件夹，保持老 Contents 单文件快照。只有用户「复制到 iCode」才按 4.8 新建包。

旧项目只有一份 HTML 的，迁成该版本文件夹里的主网页即可，不必人为拆成多文件。

## 7. 运行加载（第一期硬约束）

生成应用打开时：

1. 若是 iCode 管理的包：解析最大正式号文件夹；无正式版 → 沿用现有空/占位打开逻辑。
2. 把该文件夹当作文档根提供给嵌套页（或等价隔离环境）。
3. 主网页及相对引用从该根读取；越出该根的请求拒绝。
4. 现有存储桥、能力桥、心跳、错误桥仍要接到这个文档上，不能因为改成按目录加载而丢桥。
5. iCode 预览同一套加载器，只是根换成 `Draft`。

实现选型（Service Worker、自定义协议、请求拦截等）是实现问题，但验收标准只有一条：**版本文件夹里的相对引用能在预览和桌面两边同样工作。**

---

## 8. 建议实施顺序

按依赖往下做。每步可单独验收，不要一上来同时改编辑器、商店、导入导出。

### 8.1 包布局与只读

在应用程序卷上为 iCode 管理的包建立 `Versions`（整数正式版 + `Draft`）、版本内清单 JSON、`Developer`。正式版节点只读，草稿可写。文件管理器禁止删除正式版文件夹。确认最大号扫描排除 `Draft`。

### 8.2 按目录加载

桌面与 iCode 预览共用「以某版本文件夹为网站根」的加载。验收：主网页引用同目录脚本/样式/图片、引用子目录文件，预览和桌面都能到；引用树外路径失败；无 `index.html` 为空白页。

### 8.3 iCode 打开 / 保存 / 发布

打开 = 确保草稿（否则从最大号拷）。保存只写草稿。发布 = 升格为新最大号并只读 + 立刻新草稿并切过去。桌面仍只跑最大号。关窗后再开：无草稿则再拷。

### 8.4 砍掉内部项目列表

迁移旧注册表项目；iCode 首页改为 iCode 管理的应用；创建/删除/改名与包、桌面图标一致。删除 iCode 项目即按产品既有选择处理桌面入口（与现在「可同时卸载入口」对齐，细节跟现删除对话框，不要静默留下孤儿包）。

### 8.5 聊天与用户数据

聊天迁到开发目录；导入导出带上。用户数据继续跨版本共用，发布不清数据。

### 8.6 商店复制与导入导出

商店应用：仅复制当前在跑内容为新包 `1`，空数据、空聊天、空授权；原应用不动。导入导出整包；冲突则副本。

### 8.7 编辑器：静态多文件，仍以 HTML 为主

iCode 从「只能改一份 HTML 字符串」改为能看见草稿树、打开并保存其中文件。生成仍以主网页为主；允许把样式/脚本拆成邻居文件，并按路径打补丁。入口仍是主网页。不要在这一步引入框架或打包。

## 9. 验收清单

- 新 iCode 应用在文件管理器里能看到 `Versions/Draft`，发布后出现只读的 `1`（再发布为 `2`），桌面跑数字最大的那棵树。
- 改草稿的名字/图标/源码，桌面外观与正在跑的页面不变，直到发布。
- 发布后当前 iCode 窗口仍可继续编辑（新草稿），不会卡在只读正式版上。
- 无正式版时桌面仍能打开（占位/空态），且跑的不是草稿。
- 草稿树内相对引用在预览可用；同一套在桌面最大正式版可用；树外不可用。
- 无主网页 → 空白页。
- 文件管理器删不掉 `1`、`2` 等正式版；正式版改不了。
- 聊天在发布前后还在，且正式版文件夹里没有聊天文件可被页面请求到。
- 用户数据在发布后还在。
- 从商店复制：原应用还能打开且未被改；新图标能跑拷来的当前内容；iCode 打开后是可编辑草稿；不带商店历史和原用户数据。
- 导出再导入到空设备：版本、草稿（若当时有）、聊天、用户数据一致。导入到已有同名/同一应用的设备：得到带「副本」名的新包，而不是覆盖。
- 旧内部项目升级后无需再读 iCode 那份项目列表 JSON，桌面图标不裂成两份。
- 主网页引用同目录脚本或样式时，预览和桌面都能加载；不必为了「能跑」而把一切内联进那一份 HTML。
- 第一期微应用仍是普通 HTML/CSS/JS，没有强制 Preact、没有为微应用插入打包步骤。
