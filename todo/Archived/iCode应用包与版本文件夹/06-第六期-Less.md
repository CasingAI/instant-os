# 第六期：Less（探索优先；做不到则出报告）

> 建立时间：2026-08-25
> 期次：第六期（依赖第四期落地）
> 涉及项目：`instant-app`（iCode / 生成应用 / 应用包 / VFS）
> 状态：已实施（2026-08-25）——调查判定可以集成，走结束 A：Less 已成为工程树的系统能力
> 前置：`04-第四期-JSX工程.md`（必做）；与 `05-第五期-类型检查.md` 正交
> 总览：见同目录 `00-总览.md`

目标：弄清楚「在本系统的约束下，Less 能不能进工程树」。约束是硬的：用户浏览器里跑、无本机进程、源码在版本文件夹、发布仍打成一份单文件、解析不得逃出该版源码树。本期**先探索、再决定做不做进产品**。证明确实积不成，就停在报告，不要硬接进第四期链路。

动手时以本文为准。第四期行为在探索失败时必须原样保留（样式继续只是普通 CSS）。

---

## 1. 为什么偏探索

前面几期能拍板，是因为路径已被本仓库或官方文档钉死（文件夹版本、agent 框架、esbuild-wasm 在浏览器里打包）。Less 不是这样：打包器官方不认 Less，浏览器默认读文件方式对不上 VFS，也没有官方一体包。纸面上「先编成 CSS 再交给打包器」说得通，**不等于在嵌套页、Worker、宿主打包、跨文件引入这些接缝上一定能稳定工作。**

所以第六期允许两种合法结束，没有「必须上线 Less」这一条。

---

## 2. 两种结束方式（二选一即交差）

### A. 能集成

把 Less 做成第四期之上的系统能力：源码树可写 `.less`，可与 CSS 混用；开发面预览和发布单文件都能吃到编好的样式；跨文件引入只读该版本源码树；编译器随宿主下发，不进应用包。验收按下面「若走产品」清单。

### B. 不能集成 → 只出报告，不改产品

充分调查与最小验证之后，若判定**没有可能**在上述硬约束里集成，则**不要**把半截胶水留在主干。在本目录写一份报告（文件名自定，建议 `06-Less探索报告.md`），作为本期唯一交付。第四期保持「只有普通 CSS」。

报告至少写清：

- 调查了哪些官方文档、源码行为、宿主打包结果（要有依据，不要只靠印象）。
- 做了哪些最小试验（例如：浏览器里单独编一段 Less；插件里把 CSS 喂给 esbuild-wasm；自定义读版本树；宿主打包会不会误入 Node 入口）。
- **卡死点**是哪一条硬约束（例如：文件管理器无法接到 VFS、Worker 里编不过、产物体积/许可证/无法与单文件发布共存等）。「嫌麻烦」「没现成插件」不算不能集成。
- 明确结论：本期不上 Less；若以后约束变了（例如换了打包器），这份报告哪里可以重开。

---

## 3. 探索时仍要守的底

无论走 A 还是 B：

- 不要本机 `lessc`、不要为探索去放宽「发布后用户只开网页」。
- 不要把未验证的 Node 版 Less 插件直接打进页面。
- 不要改第四期的入口、产物同夹、桌面只跑单文件。
- 探索用的试验代码可以扔，不要在判定失败后把半截 Less 路径留在用户可走的预览/发布上。

若走 A，再遵守这些产品规则：Less 与 CSS 可混用；失败在预览可见；发布编不过就不要写入可被桌面当成功页的半截产物；嵌套页跑的是编好的 CSS，不是运行时现场编 Less。

---

## 4. 建议顺序

1. **调查：** 以当时的 Less / esbuild-wasm / 宿主打包文档和源码为准，核对浏览器入口、插件能否喂虚拟文件、默认读文件方式。
2. **最小试验：** 先单段无引入，再跨文件引入，再接到发布打单文件。每一步记下能/不能与原因。
3. **判定：** 能走通关键路径 → 收成产品（结束 A）。任一步被硬约束卡死且没有合规绕法 → 写报告（结束 B）。
4. **不要**在未判定前就把 Less 当成新应用默认骨架。

---

## 5. 验收

**结束 A：**

- 工程里能写 Less、能和 CSS 混用；预览看得到样式。
- 发布后桌面只跑单文件，其中已是 CSS。
- 跨文件引入出不了该版本源码树。
- Less 编失败：预览有原因；发布不留下假成功产物。
- 无工程入口的纯网页应用行为不变。

**结束 B：**

- 本目录有一份报告，含依据、试验、卡死点、结论。
- 产品行为与第四期结束时一致，用户侧没有 Less。
- 主干没有半截、关不掉的 Less 路径。
