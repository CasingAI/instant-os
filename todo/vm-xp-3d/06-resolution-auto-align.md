# 计划 6：分辨率自动对齐（客机感知方案 C）

> 建立时间：2026-08-24
> 依赖：无强依赖；若与计划 1（图形 PCI 设备）同期做，见第 5 节的合并建议。
> 前置实验：方案 A 已验证失败，结论见 `Instant-virtual-machine/todo/vm-xp-3d/02-resolution-poke-experiment.md`。

## 1. 背景与目标

VMware 的体验：拖动宿主窗口，客机分辨率自动跟随，画面 1:1 无缩放。我们也要这个。

方案 A（宿主直写 v86 内部 SVGA 寄存器）已实验并否决：帧缓冲尺寸确实变了、canvas 也变了，但客机 OS 完全不知道模式变化。XP 仍按旧分辨率逐行写显存，行宽错位导致画面斜向撕裂花屏（实验截图确认）。这条路线对任何「客机驱动不知道模式变了」的系统都不可用，没有补救空间。

结论：分辨率变化必须由**客机内部**发起。宿主只负责「告诉客机目标分辨率」。

## 2. 方案 C 的形态

三件事：

1. **过墙通道**：宿主 → 客机的单向小数据通道，传递目标分辨率（宽、高两个数，低频）。
2. **客机代理**：XP 里一个常驻小程序，收到分辨率后调用 `ChangeDisplaySettingsEx` 切换显示模式，走 XP 自带 VGA/SVGA 驱动的标准模式切换路径。
3. **触发**：宿主侧 ResizeObserver + debounce + 阈值（方案 A 已实现过这套 UI 侧逻辑，可回收复用设计）。

## 3. 过墙通道选型

| 路线 | 做法 | 代价 | 备注 |
|---|---|---|---|
| A. VMware Backdoor RPC | 在 v86 fork 里加极小 backdoor 设备（端口 0x5658，VMXh 魔数），只实现 `RPCI set_resolution` 一条命令 | 需 fork v86 并维护 | 与现有 `VMwareMouse` 同一兼容生态；客机侧协议公开、资料多 |
| B. 复用计划 1 的图形 PCI 设备 | 分辨率同步作为该设备的一条控制命令 | 无额外设备 | 若计划 1 确定要做，强烈倾向此路线 |
| C. 独立自定义 PIO 端口设备 | 最小虚拟设备，一个 I/O 端口写两个 u16 | 同样要 fork | 比 backdoor 更简单，但没有现成客机生态可蹭 |

**倾向**：若计划 1 落地，走 B（一块设备两个功能）；若分辨率同步要先单独落地，走 A（backdoor），因为它对客机侧工具最友好。

## 4. 客机代理（XP 侧）

- 一个 32 位常驻小程序（或 Windows 服务），轮询或阻塞等待通道上的分辨率命令。
- 收到 `(w, h)` 后：枚举显示模式确认支持 → `ChangeDisplaySettingsEx(CDS_UPDATEREGISTRY)` → XP 显示子系统重新布局桌面。
- 需要随镜像分发并设为开机自启；镜像资产管理遵循 `04-guest-image-and-files.md` 的约定（不进 git 大文件）。
- 编译工具链与 `02-guest-d3d-proxy.md` 第 3 节一致（llvm-mingw 32 位旧运行库）。

## 5. 与计划 1 的关系

计划 1 的图形 PCI 设备本来就要解决「客机 → 宿主」的批量命令通道。分辨率同步只需要「宿主 → 客机」的极小反向通道，正好是同一块设备的另一个方向。

- 若同期做：一块 PCI 设备，双向各留一条队列，分辨率同步作为第一个被使用的反向命令（还能顺便验证设备通路，比 3D 命令简单得多）。
- 若分期做：先 backdoor 单独落地分辨率，计划 1 做好后客机代理切换到 PCI 通道，backdoor 保留兼容或移除。

## 6. 接入 instant-app

- [ ] `VirtualMachineSettings` 增加「分辨率自动对齐」开关（默认关）。
- [ ] 开机配置带上开关；未开启时行为与现在完全一致（纯 CSS 缩放）。
- [ ] 开启后宿主侧 ResizeObserver 联动（debounce ~300ms、阈值 ~80px、DPR 换算、clamp 到客机驱动支持的模式列表）。
- [ ] 客机不支持/代理未安装时静默降级，不报错。

## 7. 验收阶梯

- [ ] 手动：XP 控制台里用测试工具直接向通道写 `(1280, 960)`，XP 桌面无闪烁地切换到该分辨率。
- [ ] 手动：宿主窗口拖大/拖小，客机分辨率在数秒内跟随，画面 1:1 无 CSS 拉伸。
- [ ] 边界：目标分辨率超出 2560×1600（v86 SVGA 上限）或客机不支持的模式时，clamp/拒绝并保持原状。
- [ ] 回归：开关关闭时，现有镜像行为与现在完全一致。

## 8. 风险

- fork v86 的维护成本与 `vendor:v86` 脚本冲突（同计划 1 的风险，见 `01-emulator-graphics-device.md` 第 6 节）。
- XP 模式切换会闪屏/重排图标，debounce 阈值要偏保守，避免拖窗口时连续切模式。
- 快照恢复后代理状态：分辨率同步是无状态命令，恢复后宿主重发一次当前目标值即可，无快照兼容问题。
