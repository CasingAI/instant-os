# 计划 1：模拟器图形设备（过墙）

> 依赖：无（本通路的地基）  
> 主要改：`Instant-virtual-machine` 的 v86 产物，而不是只改 TypeScript 封装。

没有这一步，客机里记下的绘制命令到不了网页。

---

## 1. 现状

- `scripts/vendor-v86.sh` 拉的是上游 copy/v86 的发行包。
- 开机选项里没有自定义图形 PCI 设备。
- 屏幕只有客机帧缓冲那一张。

v86gl 的做法是：在模拟器里加一块给图形用的 PCI 设备，客机驱动或用户态通过它做批量内存传输。原版 v86 的 VGA 仍负责桌面；三维命令走这块新设备。

---

## 2. 要做成什么样

- 模拟器能枚举出这块设备，XP 能打开它。
- 客机能把一批二进制命令写进去，网页侧能在同一拍拿到完整批次。
- 传输是单向为主：命令出去。把算好的帧写回客机显存不是这一阶段的目标。
- 快照：这块设备的队列状态要么可保存，要么规定三维加速在快照恢复后重新初始化（游戏重开设备）。先选后者更简单。

---

## 3. 接入 Instant-virtual-machine

- [ ] 决定 v86 来源：长期 fork、定期从 v86gl 同步，还是自己最小补丁。发行脚本不能再无脑覆盖成上游包。
- [ ] 开机选项增加「启用三维图形设备」，默认先关掉，避免普通 Linux/ReactOS 镜像被这块设备干扰。
- [ ] 运行时在创建模拟器时把设备打开，并把收到的批次交给计划 3 的执行器。
- [ ] 屏幕容器里预留叠加画布的位置（先可以隐藏），避免以后改 DOM 结构伤到现有缩放逻辑。
- [ ] 确认 debug / release 两套 wasm 都带这块设备，避免「本地 debug 有、生产没有」。

---

## 4. 和桌面协议

`instant-app` 暂时不必为批次本身加消息：命令在 iframe 内部消化。桌面只需要一个设置位「允许三维加速」，写进现有开机配置即可。

- [ ] `VirtualMachineSettings` 增加开关。
- [ ] 协议里的开机配置带上这个开关。
- [ ] 未启用时行为与现在完全一致。

---

## 5. 验收

- [ ] 开关关闭：现有预制镜像开机、键鼠、快照与现在无差别。
- [ ] 开关打开：网页能探测到设备存在（哪怕客机还没装驱动）。
- [ ] 用最小客机测试程序往设备写一笔固定批次，宿主能打印出长度和头几个字段。此时还不用真的画三维。

---

## 6. 风险

- 自维护模拟器 fork 会和 `vendor:v86` 冲突，必须先定更新策略。
- 现有快照内存不匹配问题（`todo/vm-snapshot-memory-mismatch.md`）在三维设备加上后会更难查，先不要让三维设备和快照复用搅在一起。
