# Windows XP 声音尾段反复播放

> 建立时间：2026-08-23  
> 涉及项目：`Instant-virtual-machine`（v86 SB16 + 浏览器扬声器链路）  
> 优先级：低（不影响开机与基本使用；XP 短音效可接受时再优化）  
> 状态：**v1 修复已落地（补丁 0008，墙钟节拍门），未经实机验证**——见文末「2026-09-15 v1」节

## 2026-09-15 v1：修复已落地（静态分析通过，未实机测试）

**改动**：`Instant-virtual-machine` 仓库新增补丁 `scripts/v86-patches/0008-sb16-dac-wallclock-pacing.patch`，落点在 `vendor/v86-src/src/sb16.js`（单文件，约 90 行新增），产物 `libv86.js` / `libv86-debug.js` 已重建，Closure 严格检查 0 error，仓库单测全绿。

**方案**：给 SB16 的 DAC 交付加「墙钟节拍门」——`dma_transfer_next` 在累计交付样本超过 `（流逝墙钟 + 300ms 超前量）× 采样率` 时不再推进 DMA、不发 IRQ，等墙钟走够再放行。恢复真实硬件「消费速率 ≈ 采样率」的语义，把「模拟器超前客机的量」从「取数泵积压决定（无界）」压回「墙钟决定（有界）」。被拦时从客机视角看这一块只是还在正常播放。

**根因核实**（对上文「根因（推断）」的确认与补充，均已落到行号）：

- autoinit 复位不等 IRQ 应答：`sb16.js` `dma_transfer_next` 内 `dma_bytes_left` 归零后同步 `raise_irq` 并立即重置计数，不读 `irq_triggered`；
- DMA 控制器那一半：`dma.js` `do_write` 在 autoinit 下把地址/计数复位初值并递归重读，即同一次请求内也可能回绕；
- 取数泵无在途门闩：`speaker.js` 宿主 `pump()` 只有 `enabled` 判断；worklet 在队列低于水位时每个 render quantum（约 2.67ms）都 postMessage，主线程卡顿时请求积压，恢复后一次性兑现成十几到几十块连抽——这就是「十几遍」的来源；
- SB16 无独立采样时钟：整个 `sb16.js` 无任何定时器，消费时机=宿主扬声器拉动时机，这是与真实硬件的本质差异；
- 上游无修复：`speaker.js` 自 2025-04 后只剩清理提交；本仓库 vendor 与钉定上游逐字节一致，升级 vendor 不能解决；v86 只有 SB16 + PC 喇叭，无第二套声卡可换。

**已覆盖的边角（静态分析）**：暂停/续播扣除暂停时长（D0/D4/D5/D6），避免恢复瞬间累积「补交额度」回绕重读；采样率变化重新起锚；传输开始（`dma_on_unmask`）起锚；节拍器不进 save state（旧存档兼容，恢复后自愈）；立体声按声道数折算帧数；单周期（非 autoinit）传输同样受门（完成 IRQ 的时机也因此贴近硬件）。

**已知边界（静态分析，待实机确认）**：

1. 主线程卡顿超过扬声器队列深度（约 100ms）时仍会出现「先静音空档、后按墙钟补交」，补交内容可能含重复，但量受墙钟限制（卡多久最多补多久），不再无界；
2. BufferSource 回退路径水位 0.2s 与 300ms slack 接近，留的裕量不大；现代浏览器走 AudioWorklet 路径，不受影响；
3. 「破音」未修——独立嫌疑：DAC 路径写死 3 倍隐藏增益（`speaker.js` `set_gain_hidden(3)`）叠加客机混音器音量（最高约 1.26 倍）后输出端无限幅器，削顶。与尾段循环无关，待单独处理。

**待实机验证清单**（恢复测试时按此过）：

1. XP 系统提示音/短 wav：播完 1 秒内安静，无尾段循环（原验收标准）；
2. 三维弹球：BGM 卡顿的形态是「回跳」还是「静音空档」；音效是否还重复（用户报告：BGM 偶发卡、音效非 100% 重复）；
3. 「客机内后台播无声音频」workaround 应可退役（用户实测它能极大缓解重复但带来破音）；
4. Win98 / Win2000 回归（原验收标准）；
5. 观测手段：`?v86=debug` 构建 + 给 V86 options 传 `log_level`（`LOG_SB16|LOG_DMA = 0x0800010`）即可打开 `[SB16]`/`[DMA]` 日志；v86 内置 `SpeakerDACDebugger` 可 dump CSV，比对连续队列块是否字节相同可直接坐实/排除回绕重读。

**后续可调**（暂不动，等实机数据）：在节拍门兜底的前提下加深 worklet 的 `QUEUE_RESERVE`（当前 1024 源样本）可提升卡顿容忍度，代价是音效延迟，需实机调参。

## 现象

在 `Instant-virtual-machine` 里运行 Windows XP，声音能正常从头播到尾，但结尾一小段会反复播放，常达十几次甚至更久。整体听感卡顿，不像单纯的爆音或变速。

客机内已按 v86 文档配置：Standard PC、手动安装 Sound Blaster 16 WDM 驱动、扬声器在虚拟机设置中开启。调整硬件加速、采样率等 XP 声音选项无效。

## 根因（推断）

客机侧声音能完整播出，说明声卡、中断、驱动基本可用。问题出在**一段缓冲播完之后的衔接**：

1. XP 的 SB16 WDM 驱动使用 DMA 自动循环模式：一块内存播完后应触发中断，由客机填下一块或发停止。
2. v86 的 SB16 在整块计数归零时会立刻把「剩余字节」重置并继续抽同一块内存，同时向 CPU 发中断。
3. 浏览器侧的播放队列按自己的时钟持续向模拟器要数据，不会等客机处理完中断。
4. 若客机（XP + WDM）在中断处理上偏慢，或播放队列一次要的数据偏多，最后那一小块会在客机尚未更新缓冲前被**重复抽取多次**送扬声器。

这与 QEMU 上 SB16「冻住并循环最后一小段」类问题同源，属于模拟器与客机驱动时序不匹配，**不是** XP 里再调一个隐藏开关能解决的。

Instant-virtual-machine 当前仅透传 v86 的 `disable_speaker` 开关，无第二套声卡（如 AC97）可换。

## 已排除的无效方向

- 客机：DirectSound 硬件加速拉到无、降低采样率、确认 IRQ/DMA 资源
- 宿主：仅开关扬声器、调内存/ACPI（Standard PC 仍需要，但不治尾段循环）

## 待办（未来视情况优化）

### 1. 在 v86 SB16 层收紧「播完一块」后的行为

位置：`Instant-virtual-machine` 内嵌的 v86（`public/vendor/v86` 或 vendor 源码）。

思路：DMA 块计数归零并发出中断后，在客机应答中断或显式停止之前，**不要**立即按 autoinit 继续抽下一块；或限制连续抽取次数，避免同一尾段被排队十几遍。

需对照真实 SB16 与 Windows WDM 驱动的双缓冲语义，避免修尾段循环却弄坏连续播放。

### 2. 在浏览器扬声器层避免空转要数据

位置：v86 `speaker` 模块（AudioWorklet / BufferSource 两条 DAC 路径）。

思路：播放队列见底时，若 SB16 侧已无新样本且处于「等中断」状态，暂停 pump，而不是用空缓冲或重复块填满队列。

### 3. 验收标准

- XP 系统提示音、短 wav：播完后 **1 秒内** 安静，无尾段循环。
- 连续音乐/较长 wav：可接受轻微断续，但不应在句末卡死十几遍。
- Win98 / Win2000 回归：不因改动导致原本可用的场景变坏。

### 4. 可选：文档与用户预期

- 在虚拟机帮助或 XP 相关说明中注明：当前 SB16 在 XP 上尾段可能循环，属已知限制。
- v86 上游若已有相关 issue/PR，升级 vendor 时一并跟进。

## 决策点

- 是否值得 fork/patch v86，还是等上游修复后再升级 vendor？
- 优化优先级是否低于 `todo/vm-xp-3d/` 三维通路（建议：是，除非用户强依赖 XP 内音效）？
- 若短期不修：是否仅在 XP 预设/文档里标注「声音已知问题」，避免用户反复试客机设置？
