# vm-remote-control · 05 文件双向传输调研（只调研，不实现）

> 2026-08-28。原五期任务：探索宿主（Instant OS）↔ 客机（XP）文件双向传输的实现路径，
> 硬约束：**大量文件传输不能阻塞 PING 等控制面消息**。本文只做方案对比与结论，
> 不附实现计划。前置事实：v3 已落地的共享内存信箱（`01-roadmap.md` §2.2）是
> 现成的数据面底座；9p 方案已排除（见 §4）。

## 0. 结论先行

| 候选 | 吞吐 | 控制面阻塞风险 | XP 侧工程量 | 缓存一致性风险 | 结论 |
|---|---|---|---|---|---|
| A 信箱分块 | 中（~100KB/s 量级） | 无（纯 DMA 数据面） | 小（ring3 就够） | 无 | **推荐先做** |
| B 镜像直写 | 高（受 IDE 模拟限） | 无（纯 DMA） | 大（XP 运行中直写 FAT/NTFS） | **高，XP 拒载风险** | 仅关机态可用 |
| 9p | 高 | — | — | — | **排除**（XP 无客户端） |

推荐路线：**A 为主，B 的关机态变体作为大批量场景的补充**。A 的吞吐对
「文档/截图/小工具」级别的日常传输足够；GB 级镜像传输走 B（且只在关机态做，
宿主本来就有镜像写回通路，等于零客机代码）。

## 1. 候选 A：信箱分块传输（现成信箱上扩协议）

### 1.1 原理

把 64KB 信箱当一个「DMA 网卡」：控制面握手之后，文件按块（例如 32KB 数据 +
块头）流过分块缓冲。方向双向对等：

```
宿主 → 客机（写入 XP 的 C:\Tools\）：宿主把块写进 H2G → 桥/agent 收块 →
  WriteFile 落盘 → status=2 确认 → 宿主发下一块
客机 → 宿主：对称，G2H 方向
```

需要的协议扩展（全部是信箱头之后的约定，不动 ivm-shm.sys）：
- 会话帧：`[magic][seq][op: OPEN/ DATA/ACK/CLOSE][offset u64][len u32][path…]`；
  OPEN 带目标路径与总大小，DATA 带块载荷，CLOSE 带内容校验；
- 现有 status 三态够用（1 就绪 / 2 已读即 ACK）；seq 已有，防重放。
- 信箱容量是瓶颈：64KB 里单块最多 ~32KB 数据。吞吐 ≈ 32KB / (200ms 轮询 + XP 侧落盘)，
  量级 100KB/s 上下——够日常，不够批量。

### 1.2 工程量与风险

- XP 侧：clipboard-bridge 同款 ring3 程序即可（新增 file-bridge 或并入 agent），
  无驱动改动；CreateFile/WriteFile 都是 ring3 合法调用。
- 阻塞约束天然满足：数据面全在 v86 内存读写（`read_memory/write_memory` 是
  纯 JS，不占 CPU 时间片；v86 200ms 轮询周期与 5s PING 完全独立）。
- 校验：块级 CRC 或整体 SHA-256（宿主算，XP 侧 wvsprintf 级别的 C 代码不擅长
  密码学——用简单 CRC32 逐块 + CLOSE 总长核对即可，传输层有 seq 防重放）。
- 中断恢复：OPEN 记录 offset，重连后从最后 ACK 的块续传；信箱清零（重开机）
  等价会话作废，从头再来。

## 2. 候选 B：镜像直写（不经客机文件系统）

### 2.1 原理

文件在 XP 里最终也是硬盘镜像里的扇区。宿主已经拥有镜像的全部访问通路
（disk stream 挂载 + `diskWrite` 回写，`virtual-machine-disk-stream-host.ts`）：
把「传文件」变成「宿主直接改镜像里的文件系统」——解析镜像 FAT32/NTFS 结构，
定位目录项与簇链，写入数据与目录项，XP 里文件凭空出现。

### 2.2 致命约束：XP 运行中直写 = 缓存一致性灾难

XP 的文件系统缓存、卷脏位、元数据都在内存里，宿主绕过它改扇区：
- XP 缓存里的旧目录项会在任意时刻把「已出现的文件」写回成不存在；
- FAT/NTFS 日志（NTFS $LogFile / USN）与实际数据脱节 → **chkdsk 或 XP 拒载**
  （与 v3 排查过的 `.reloc` 根因同级别的「镜像结构被运行中系统看到不一致」问题）；
- 宿主读镜像的时机与 XP 回写交错，读到的也是半旧半新。

**结论：B 只在关机态成立**（XP 不再回写，镜像静止）。关机态下它其实是现有
「镜像挂载 + 回写」能力的自然延伸：宿主解析镜像文件系统直接种文件。
工程量集中在镜像文件系统的解析与安全写入（FAT32 目录项/簇链管理，或引入
第三方库），且 NTFS 写支持远比 FAT32 危险（日志回放会否决外来改动）。

### 2.3 适用边界

- XP 开机 → 传小文件：A；
- XP 关机 → 种一批文件/提取整批文件：B（FAT32 镜像优先）；
- XP 运行中 → 大文件：**没有好方案**（A 吞吐不够，B 危险），接受它不存在。

## 3. 客机侧「文件提取」的第三种思路（备忘，不计入候选）

EXEC_R 已经能在 XP 里跑任意命令：`makecab`/`tar`（XP 无）打包 + 信箱传输，
或者干脆 `debug.exe`/VBScript 生成自解压包。这属于 A 的应用层组合，不单独成方案。

## 4. 已排除：9p 文件系统共享

v86 支持 9p 服务端（`V86Options.filesystem`），但那是给 Linux 客机的
（内核 v9fs 驱动）；**Windows XP 没有 9p 客户端驱动**，路不通。同理排除的
还有 SMB/网络方案（v86 网络后端只有 fetch 代理形态，没有可用的双向 TCP）。
